# HireRight — Amazon S3 + Neon storage reference

> **Stack:** React (Vite) + **Node/Express** API + **Neon PostgreSQL**. S3 via `@aws-sdk/client-s3`.  
> **Layout version:** **2** (`backend/node/storage/s3Namespace.mjs`). Inspect live schema: `GET /health` → `objectStorage.layout`.  
> **Legacy spec:** Sections 1–13 below are the original implementation brief. **Section 15** is the maintained, code-accurate reference.

## 15. Storage reference — S3 + Neon (layout v2)

### 15.1 Design principles (industry-aligned)

| Principle | How HireRight applies it |
|-----------|---------------------------|
| **Single private bucket** | One `S3_BUCKET` per environment; no per-tenant buckets. |
| **Multi-tenant key prefix** | All objects under `tenants/{tenantId}/…` (isolation by prefix + auth). |
| **Bytes in S3, index in Postgres** | File bodies never stored in Neon; Neon holds **metadata + pointers** only. |
| **Structured JSON in Neon** | Scores, Q&A summaries, profile fields, session state — queryable app data. |
| **No trusted client keys** | API builds object keys server-side; downloads use presigned URLs after ownership checks. |
| **Active bucket only** | Rows with `bucket ≠ S3_BUCKET` are ignored (no cross-account leakage after migration). |

### 15.2 What lives where (boundary)

| Data | **Amazon S3** (files) | **Neon** (structured / metadata) |
|------|----------------------|----------------------------------|
| Resume PDF/DOCX bytes | Yes — `…/resumes/resume_v{n}_{uuid}.ext` | `stored_files` + profile pointers; optional **extracted text** in `profiles.data.resumeText` for search/AI |
| Interview video (WebM/MP4) | Yes — `…/recordings/recording_{id}.ext` | `interview_recordings` (key, bucket, size, status) |
| Full transcript JSON (Q&A export) | Yes — `…/transcripts/transcript.json` | `interview_artifacts` (`artifact_type = transcript`); **not** a second copy of the JSON blob |
| Scorecard PDF | Yes — `…/reports/interview_report.pdf` | `interview_artifacts` (`artifact_type = report`) |
| Scorecard dimensions, overall %, rubric | No (PDF is presentation) | `interview_results.data` (JSONB), `interview_result_history` |
| Session runtime (questions, progress) | No | `interview_sessions.data` (JSONB) |
| Users, orgs, jobs, applications | No | `users`, `organizations`, `jobs`, `employer_applications`, etc. |

**Rule:** If it is a **file** (PDF, video, large JSON artifact), the canonical copy is **S3**. Neon stores **`bucket` + `s3_object_key` / `object_key`** and fields needed for auth, listing, and presigning — not duplicate file bytes.

### 15.3 S3 object-key layout (v2 — current uploads)

All keys are generated in `backend/node/storage/s3KeyLayout.mjs`. Segments are sanitized; filenames are not used as raw keys.

```text
s3://{S3_BUCKET}/
└── tenants/
    └── {tenant_id}/                          ← org id or "platform" (S3_DEFAULT_TENANT_ID)
        └── candidates/
            └── {candidate_id}/               ← users.id preferred, else sanitized email
                ├── resumes/
                │   └── resume_v{n}_{uuid}.pdf
                ├── certificates/
                │   └── {document_id}.pdf      ← reserved; upload UI not wired yet
                └── interviews/
                    └── {session_id}/          ← interview_sessions.session_id
                        ├── transcripts/
                        │   └── transcript.json
                        ├── reports/
                        │   └── interview_report.pdf
                        └── recordings/
                            └── recording_{uuid8}.webm
```

**Tenant resolution:** `session.organizationId` → user `primaryOrganizationId` → `platform`.

**Legacy (read-only / ignored after bucket change):**

- `resumes/{email}/…` — pre-tenant resumes  
- `tenants/{tenant}/interviews/{session}/…` — flat interview paths (v1); new uploads use **candidate-scoped** paths above  

### 15.4 Neon tables — file metadata (S3 pointers)

Defined in `backend/node/db/schema-files.sql`. Applied with `npm run db:init`.

#### `stored_files` — candidate resumes (and future generic files)

| Column | Purpose |
|--------|---------|
| `id` | Primary key; exposed as `profiles.data.resumeFileId` |
| `owner_email`, `owner_user_id` | Ownership |
| `storage_provider` | `'s3'` or `'supabase'` (legacy) |
| `bucket` | Must match `S3_BUCKET` to be served |
| `object_key` | Full S3 key under `tenants/…/resumes/…` |
| `tenant_id`, `entity_id`, `file_category`, `version_number` | Versioning & tenant scope |
| `original_filename`, `content_type`, `byte_size`, `status` | Display & validation |

**Profile JSON pointers** (`profiles.data`, merged on upload):

- `resumeStoragePath` → same as `object_key`  
- `resumeFileId` → `stored_files.id`  
- `storageProvider` → `'s3'`  
- `resumeUrl` → API path `/api/resume/download` (not a public S3 URL)

#### `interview_recordings` — video metadata

| Column | Purpose |
|--------|---------|
| `id` | Recording row id (presigned upload flow) |
| `tenant_id`, `interview_id` | Scope (`interview_id` = session id) |
| `candidate_email`, `candidate_id` | Candidate ownership |
| `s3_object_key`, `bucket` | S3 location |
| `status` | `pending` → `uploading` → `uploaded` / `failed` |
| `file_size_bytes`, `duration_seconds`, `content_type` | Playback & validation |

#### `interview_artifacts` — transcript + report PDF

| Column | Purpose |
|--------|---------|
| `interview_id` | Session id (unique per `artifact_type`) |
| `artifact_type` | `'transcript'` \| `'report'` \| `'audio'` |
| `s3_object_key`, `bucket` | S3 location |
| `candidate_email`, `tenant_id` | Access control |
| `byte_size`, `content_type`, `status` | HeadObject / presign |

**Uniqueness:** one row per `(interview_id, artifact_type)` — upsert on re-score/regenerate PDF.

### 15.5 Neon tables — interview & profile (not S3 file bodies)

| Table | Role vs S3 |
|-------|----------------|
| `interview_sessions` | Runtime session JSON (`data`): consent, org, job, in-progress Q&A — **not** the transcript file |
| `interview_results` | Latest scorecard **structured** result per email (`data` JSONB): overall, dimensions, `sessionId` — used for UI; PDF is generated to S3 |
| `interview_result_history` | Append-only score history for analytics |
| `profiles` | Wizard + `resumeText` (parsed text for LLM/search); S3 pointers as in §15.4 |
| `users`, `organizations`, `jobs`, `employer_applications` | SaaS core; no file bytes |

Optional structured assessment module (separate flow): `schema-assessment.sql` — `assessment_resumes.extracted_text` is **assessment-only** text in Neon, not the main HireRight resume S3 path.

### 15.6 End-to-end flows

```text
Resume upload
  Browser → POST /api/resume/upload (auth)
  → PutObject S3 (tenants/…/resumes/…)
  → INSERT stored_files (bucket, object_key, …)
  → PATCH profiles.data (resumeFileId, resumeStoragePath, …)

Interview score (POST /api/interview/score)
  → UPDATE interview_results / session in Neon (structured result)
  → PutObject transcript.json → upsert interview_artifacts (transcript)
  → Generate PDF (Playwright) → PutObject interview_report.pdf → upsert interview_artifacts (report)

Interview recording finish
  → POST …/recordings/upload-url → INSERT interview_recordings (pending)
  → Browser presigned PUT → S3 …/recordings/recording_*.webm
  → POST …/recordings/complete → status uploaded

Employer / candidate download
  → Load Neon row (filter bucket = S3_BUCKET)
  → HeadObject + presigned GET (never return permanent S3 URL)
```

### 15.7 API surface (file-related)

| Method | Path | S3 action |
|--------|------|-----------|
| POST | `/api/resume/upload` | Server PutObject resume |
| GET | `/api/resume/download` | Presigned GET resume |
| POST | `/api/interview/recordings/upload-url` | Presigned PUT recording |
| POST | `/api/interview/recordings/complete` | Finalize metadata |
| GET | `/api/interview/artifacts/{sessionId}/transcript\|report/download` | Presigned GET artifact |
| GET | `/api/vendor/candidate-documents/resume\|report\|recording` | Employer presigned access |
| POST | `/api/interview/artifacts/report` | Optional browser PDF upload (fallback) |

### 15.8 Environment & operations

```env
AWS_REGION=ap-south-2
S3_BUCKET=your-bucket-name
AWS_ACCESS_KEY_ID=…
AWS_SECRET_ACCESS_KEY=…
# Optional:
S3_DEFAULT_TENANT_ID=platform
S3_PRESIGN_EXPIRES_SECONDS=900
S3_MAX_RECORDING_BYTES=104857600
S3_MAX_REPORT_BYTES=12000000
S3_EXPECTED_BUCKET=          # must match S3_BUCKET if set
DISABLE_SUPABASE=true          # recommended: S3-only files
```

### 15.9 IAM (minimum)

On bucket `arn:aws:s3:::BUCKET`:

- **Objects:** `s3:PutObject`, `GetObject`, `HeadObject`, `DeleteObject` on `arn:aws:s3:::BUCKET/*`
- **Optional (console list / HeadBucket):** `s3:ListBucket`, `GetBucketLocation` on `arn:aws:s3:::BUCKET`

- Frontend: React
- Backend: FastAPI (Python)
- Existing database: Neon PostgreSQL
- Cloud file storage: Amazon S3
- AI features: Resume parsing, interview question generation, candidate answers, interview evaluation, and potentially speech-to-text and text-to-speech.

First, inspect the entire existing repository. Understand the current database models, API endpoints, authentication, authorization, candidate workflows, employer workflows, interview recording implementation, and file upload logic.

**Do not rewrite the application from scratch.** Integrate S3 into the existing architecture and preserve all currently working functionality.

## 3. Exact Amazon S3 Object-Key Structure

Use the following object-key naming convention inside my existing S3 bucket.

Do not create a separate S3 bucket for every candidate, interview, or company.

```text
{S3_BUCKET}/
└── tenants/
    └── {tenant_id}/
        └── candidates/
            └── {candidate_id}/
                ├── resumes/
                │   └── resume_v{n}_{uuid}.pdf
```

> **Canonical detail:** see **§15.3** (layout v2). Older flat paths `tenants/{tenant}/interviews/{id}/…` may exist in the bucket from earlier releases; new code writes under `candidates/{id}/interviews/…`.

The paths above describe the required naming convention, not actual folders that must be created manually.

Requirements:

- Generate unique object keys to prevent accidental overwriting.
- Support multiple resume versions.
- Support multiple recording files or recording segments for an interview.
- Use the actual authenticated tenant, candidate and interview IDs from the database.
- Never trust tenant IDs, candidate IDs or interview IDs supplied by the frontend without verifying authorization.
- Preserve the original filename in metadata where appropriate.
- Sanitize filenames and never use raw user filenames as trusted object keys.
- Store files only in the correct tenant's namespace.
- Use the existing bucket configured through environment variables.

## 4. Exact Responsibilities of Amazon S3

Store the actual binary files and large file artifacts in S3.

### A. Candidate resumes

Support the existing application's accepted resume formats, including PDF and DOCX where appropriate.

Requirements:

- Upload resumes to `tenants/{tenant_id}/candidates/{candidate_id}/resumes/`.
- Generate unique, versioned object keys.
- Save the original filename, content type, file size, object key and upload timestamp.
- Link the resume to the correct candidate in Neon.
- Preserve the current resume parsing workflow.
- If the application extracts text from a resume, keep the structured extracted data in Neon when it is used by the application's queries. Store large parsing artifacts in S3 only when needed.
- Do not break existing resume upload, preview, parsing or replacement functionality.

### B. Interview video recordings

Implement actual interview recording storage, not just a database field.

Requirements:

- Inspect whether browser-based interview recording already exists.
- If it exists, integrate its upload workflow with S3.
- If it does not exist, implement browser recording using supported browser APIs such as MediaRecorder, with appropriate camera/microphone permission handling.
- Support the recording formats that the implementation actually produces, such as WebM, and MP4 only where supported by the selected recording or transcoding approach.
- Upload video recordings to `tenants/{tenant_id}/interviews/{interview_id}/recordings/`.
- Support large files using S3 multipart upload or another resumable upload strategy.
- For long interviews, support chunked or multipart uploading where appropriate.
- Prevent duplicate submissions and accidental overwriting.
- Track upload progress, completion, failure and retry states.
- Associate each recording with the correct interview and candidate.
- Store the actual object key and metadata in Neon.
- Provide an authorized playback/download flow for permitted candidates or employers.
- Never make recordings publicly accessible.
- Handle interrupted uploads and abandoned multipart uploads safely.

Before recording begins, ensure the interface clearly requests the necessary camera/microphone permissions and presents appropriate recording consent information.

### C. Interview audio recordings

If the current application records or separately processes audio:

- Store audio files in `tenants/{tenant_id}/interviews/{interview_id}/audio/`.
- Use the actual audio format generated by the application.
- Store the S3 object key and metadata in Neon.
- Do not create duplicate audio files if the application's video already provides the audio needed for processing.
- Keep existing speech-to-text and text-to-speech functionality working.

### D. Interview transcripts

If transcription is implemented:

- Store optional transcript JSON or large transcript artifacts in `tenants/{tenant_id}/interviews/{interview_id}/transcripts/`.
- Include transcript text, timestamps and speaker identifiers when available and appropriate.
- Keep searchable transcript text and essential question-answer associations in Neon if the application needs them for queries, reporting or evaluation.
- Do not store a transcript in S3 only to avoid adding a database field that the application needs to query frequently.

### E. Certificates and supporting documents

If the existing application supports certificates or supporting documents:

- Store the actual files under `tenants/{tenant_id}/candidates/{candidate_id}/certificates/`.
- Save the file metadata and S3 object key in Neon.
- Do not invent new document workflows if the current product does not support them.

### F. Generated interview reports

If the application generates downloadable PDF interview reports:

- Store the actual generated PDF in `tenants/{tenant_id}/interviews/{interview_id}/reports/`.
- Save its object key and metadata in Neon.
- Keep evaluation scores, summaries, recommendations and structured report data in Neon so they can be queried without downloading a PDF.
- Do not generate duplicate reports unnecessarily.

## 5. Exact Responsibilities of Neon PostgreSQL

Continue using the existing Neon PostgreSQL database for structured, relational application data.

Inspect and reuse existing tables before creating migrations.

The database should contain the following logical data, using existing equivalent models wherever possible:

- Users and authentication records
- Candidates and candidate profiles
- Employers and company accounts
- Jobs and job requirements
- Applications
- Resume metadata and S3 object keys
- Interview sessions and their status
- Interview questions
- Candidate answers
- Scores, feedback and evaluation results
- Recording metadata and S3 object keys
- Transcript text or searchable transcript data where required
- Generated report metadata and S3 object keys
- File-processing statuses and timestamps
- Tenant relationships and access-control data
- Relevant audit events

Do not store video, audio, PDF or DOCX binary content directly in PostgreSQL.

### Recording metadata

Create a new table or adapt an existing table to represent interview recordings.

The logical model should include:

- `id`
- `tenant_id`
- `interview_id`
- `candidate_id`, if consistent with the current schema
- `s3_object_key`
- `original_filename`
- `content_type`
- `file_size_bytes`
- `duration_seconds`, nullable until known
- `status`
- `created_at`
- `updated_at`

Use the project's existing ID types, naming conventions, ORM and migration framework. Do not copy these field types blindly.

Possible recording statuses include:

- `pending`
- `uploading`
- `uploaded`
- `processing`
- `completed`
- `failed`
- `deleted`

Only use statuses that fit the implemented workflow. Define valid transitions and handle failures consistently.

### File metadata

If appropriate for the existing schema, implement or extend a reusable file metadata model with:

- File ID
- Tenant ID
- Owner/entity ID
- File category
- Original filename
- S3 object key
- MIME/content type
- Size in bytes
- Processing status
- Created and updated timestamps

Use appropriate foreign keys, indexes and constraints. Keep relationships consistent with the existing data model.

## 6. FastAPI Backend Implementation

Use `boto3` or the appropriate AWS SDK for Python.

Implement reusable S3 storage services instead of duplicating S3 code across endpoints.

Required functionality:

- Upload files
- Generate authorized, short-lived presigned upload URLs when direct browser-to-S3 upload is appropriate
- Generate authorized, short-lived download or playback URLs
- Start, complete and abort multipart uploads when required
- Delete files when the authorized application workflow requires deletion
- Check object metadata where needed
- Save and update file metadata in Neon
- Handle S3 and database errors safely
- Prevent unauthorized cross-tenant access
- Validate upload size, file type and ownership
- Avoid logging presigned URLs, credentials or sensitive file contents

Prefer presigned direct-to-S3 uploads for large video files so that video bytes do not need to pass through FastAPI. FastAPI must authenticate the user, authorize the target interview, generate the upload authorization and record or finalize the metadata.

Never allow the frontend to submit an arbitrary S3 key and then retrieve or delete that object without server-side ownership checks.

Use the existing authentication system and authorization middleware. Do not bypass current access controls.

## 9. Security Requirements

Implement and verify the following:

- Private S3 bucket only.
- S3 Block Public Access remains enabled.
- Server-side encryption enabled.
- Least-privilege AWS permissions for the required bucket and object operations.
- Short expiration periods for presigned URLs.
- Server-side authentication and authorization for every file operation.
- Tenant isolation on upload, playback, download and deletion.
- Validate file size and MIME type, and do not trust browser-provided content types alone.
- Use safe object keys and prevent path manipulation.
- Do not expose permanent S3 URLs or credentials in API responses.
- Do not allow one employer to access another employer's candidates or recordings.
- Avoid exposing recordings through public static hosting or unauthenticated endpoints.
- Implement a retention/deletion approach consistent with product policy and applicable privacy requirements.
- Ensure deletion and database metadata updates do not leave files unintentionally accessible.
- Add suitable audit logging for sensitive file access and deletion, without logging secrets.

Do not modify AWS Console configuration or create cloud resources automatically. Assume the bucket and IAM permissions will be configured separately.
